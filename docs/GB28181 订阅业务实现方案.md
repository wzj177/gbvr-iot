下面我按你给的 4 个场景，用一个“典型 GB28181 SIP Server（像 WVP / LiveGBS 这类结构）”的**伪代码**把链路写全：订阅下发、定时续订/退订、NOTIFY 转发到业务 API、以及“实时直播/录像/快照”如何和**报警预案的录像时长/快照周期**联动。

> 依据 GB/T 28181-2022：事件订阅用 **SUBSCRIBE**，通知用 **NOTIFY**，并且订阅/通知的 Content-Type 是 `Application/MANSCDP+xml`；订阅体里不同事件对应不同 `CmdType`（Catalog / Alarm / MobilePosition / PTZPosition）。

### 1.3 ensureSub：真正发送 SUBSCRIBE（含 dialog 复用）

> Catalog 的 `CmdType=Catalog`；Alarm 的 `CmdType=Alarm`；移动位置订阅 `CmdType=MobilePosition` 且可带 `Interval`；PTZ 精准状态查询或订阅 `CmdType=PTZPosition`。

```java
void ensureSub(String deviceId, EventType type, boolean enable) {
  SubscribeSession s = db.gb_subscribe_session.find(deviceId, type);

  if (enable) {
    if (s == null || s.status != ACTIVE) {
      // 首次订阅
      sendSubscribe(deviceId, type, /*expires*/3600, /*reuseDialog*/false);
    } else if (s.expires_at.minusMinutes(5).isBefore(now())) {
      // 快过期：续订（复用 dialog）
      sendSubscribe(deviceId, type, 3600, /*reuseDialog*/true);
    }
  } else {
    if (s != null && s.status == ACTIVE) {
      // 退订：Expires=0（复用 dialog）
      sendSubscribe(deviceId, type, 0, /*reuseDialog*/true);
    }
  }
}
```

### 1.4 sendSubscribe：构建 SIP SUBSCRIBE（消息体是 MANSCDP XML）

订阅总体要求：SUBSCRIBE + `Content-Type: Application/MANSCDP+xml`。

```java
void sendSubscribe(String deviceId, EventType type, int expiresSec, boolean reuseDialog) {
  DeviceEndpoint ep = sipRegistry.getEndpoint(deviceId); // remote ip/port + contact + uri

  SubscribeSession s = reuseDialog ? db.session.get(deviceId, type) : null;

  SipRequest req = new SipRequest("SUBSCRIBE", ep.remoteUri);
  req.headers["Content-Type"] = "Application/MANSCDP+xml";
  req.headers["Expires"] = String.valueOf(expiresSec);

  if (reuseDialog && s != null) {
    // RFC6665：复用 dialog
    req.headers["Call-ID"] = s.call_id;
    req.headers["From"]    = buildFromWithTag(localId(), s.from_tag);
    req.headers["To"]      = buildToWithTag(ep.id, s.to_tag);
    req.headers["CSeq"]    = (s.cseq + 1) + " SUBSCRIBE";
  } else {
    // 新 dialog
    req.headers["Call-ID"] = genCallId();
    req.headers["From"]    = buildFromWithNewTag(localId());
    req.headers["To"]      = buildTo(ep.id);
    req.headers["CSeq"]    = "1 SUBSCRIBE";
  }

  req.body = buildSubscribeBodyXml(type, deviceId /*或 systemId*/, /*interval*/5, /*alarmFilter*/null);

  SipResponse resp = sipTransport.send(req);

  if (resp.is2xx()) {
    // 保存/更新 dialog（从响应里拿 To-tag）
    upsertSessionFromSubscribeResp(deviceId, type, req, resp, expiresSec);
  } else {
    db.session.markFailed(deviceId, type, resp.status + " " + resp.reason);
  }
}
```

### 1.5 buildSubscribeBodyXml：4 种订阅 XML

> 这些 `CmdType` 在标准里明确：Catalog / Alarm / MobilePosition / PTZPosition。

```java
String buildSubscribeBodyXml(EventType type, String targetDeviceId, int intervalSec, AlarmFilter f) {
  String sn = genSN();

  switch (type) {
    case CATALOG:
      // A.2.4.3：CmdType=Catalog，可带 StartTime/EndTime 做增量目录订阅 :contentReference[oaicite:4]{index=4}
      return """
      <Query>
        <CmdType>Catalog</CmdType>
        <SN>%s</SN>
        <DeviceID>%s</DeviceID>
        <!-- 可选: StartTime/EndTime -->
      </Query>
      """.formatted(sn, targetDeviceId);

    case ALARM:
      // A.2.4.6：CmdType=Alarm，可带级别/方式/类型/时间过滤 :contentReference[oaicite:5]{index=5}
      return """
      <Query>
        <CmdType>Alarm</CmdType>
        <SN>%s</SN>
        <DeviceID>%s</DeviceID>
        <!-- 可选过滤: StartAlarmPriority/EndAlarmPriority/AlarmMethod/AlarmType/StartAlarmTime/EndAlarmTime -->
      </Query>
      """.formatted(sn, targetDeviceId);

    case MOBILE_POSITION:
      // A.2.4.9：CmdType=MobilePosition，可带 Interval（秒，默认5） :contentReference[oaicite:6]{index=6}
      return """
      <Query>
        <CmdType>MobilePosition</CmdType>
        <SN>%s</SN>
        <DeviceID>%s</DeviceID>
        <Interval>%d</Interval>
      </Query>
      """.formatted(sn, targetDeviceId, intervalSec);

    case PTZ_POSITION:
      // A.2.4.13：CmdType=PTZPosition（精准状态查询或订阅） :contentReference[oaicite:7]{index=7}
      return """
      <Query>
        <CmdType>PTZPosition</CmdType>
        <SN>%s</SN>
        <DeviceID>%s</DeviceID>
      </Query>
      """.formatted(sn, targetDeviceId);

    default:
      throw new IllegalArgumentException();
  }
}
```

## 2）Schedule Job：需要一个“续订/退订巡检”的 job 吗？

**需要，但不是“拉取订阅数据”。**
订阅是设备通过 NOTIFY 推送；job 的职责是：

* **续订**：快到期时，复用 dialog 发 `SUBSCRIBE Expires=3600`
* **退订兜底**：用户配置已关，但 session 还 ACTIVE，就发 `Expires=0`
* **离线补偿**：设备重新注册上线后，把 pending 的订阅补发

```java
@Scheduled(every = "1min")
void subscriptionHousekeepingJob() {
  // 1) 续订：5 分钟内过期的 ACTIVE session
  for (SubscribeSession s : db.session.findExpiringSoon(minutes=5)) {
    if (sipRegistry.isOnline(s.device_id)) {
      sendSubscribe(s.device_id, s.event_type, 3600, true);
    }
  }

  // 2) 退订：配置为 0 但 session 仍 ACTIVE 的
  for (SubscribeSession s : db.session.findShouldBeStopped()) {
    if (sipRegistry.isOnline(s.device_id)) {
      sendSubscribe(s.device_id, s.event_type, 0, true);
      db.session.markStopped(s);
    }
  }

  // 3) 离线补偿：设备上线后补发 pending 配置
  for (String deviceId : db.device_sub_cfg.findPendingDeviceOnline()) {
    reconcileSubscriptions(deviceId, db.device_sub_cfg.get(deviceId));
    db.device_sub_cfg.clearPending(deviceId);
  }
}
```

```java
void onUserDisableAllSubscriptions(String deviceId) {
```

### 4.1 收到 NOTIFY：解析 XML → 转发 API

#### 建议你的转发 JSON（统一封装，方便你后端 API）

```json
  "channelId": "34020000001320000109", 
  "gb": {
    "cmdType": "Alarm|Catalog|MobilePosition|PTZPosition",
    "sn": "62",
    "rawXml": "<Notify>...</Notify>"

```

#### 伪代码

```java
void onSipNotify(SipRequest notifyReq) {
  assert notifyReq.method == "NOTIFY";
  assert notifyReq.headers["Content-Type"].contains("Application/MANSCDP+xml");

  String rawXml = notifyReq.body;
  ParsedManscdp m = manscdpParser.parse(rawXml); // 解析 CmdType/SN/DeviceID/...

  ApiPayload payload = new ApiPayload();
  payload.event = mapCmdTypeToEvent(m.cmdType);         // Alarm/Catalog/MobilePosition/PTZPosition
  payload.deviceId = m.deviceId;
  payload.channelId = guessChannelId(m);                // 目录/报警里可能带通道项
  payload.gb.rawXml = rawXml;
  payload.gb.cmdType = m.cmdType;
  payload.gb.sn = m.sn;
  payload.data = m.toJson();

  http.post(BIZ_API + "/gb/notify", payload);

  sipTransport.reply200(notifyReq); // NOTIFY 必须回 200 OK
}
```

## 4.2 报警事件 → 联动“预案录像时长 + 快照周期 + ZLM 抓拍(getSnap)”

你前面已经决定：**报警订阅是设备管理配置做；报警预案只是匹配条件+动作**。所以流程是：

1. 收到 Alarm NOTIFY（或 MESSAGE 报警上报，取决于设备实现）
2. 落库 `gv_alarm_event`
3. 找到命中的 `gv_alarm_plan`（按通道关联 + 级别/方式/type/eventtype 匹配）
4. 如果预案要求录像：**发起实时 INVITE 建立 live 流 → ZLM startRecord → 到时 stopRecord + BYE**
5. 如果预案要求抓拍：在录像窗口内按 `snapshot_interval_sec` 调 ZLM `getSnap`，落库 `gv_snapshot_file`
6. 将生成的 `record_file.id` / `snapshot_file.id` 关联到 `gv_alarm_event_asset`

### 4.2.1 伪代码：报警事件处理器

```java
void onAlarmEvent(AlarmEvent alarm) {
  long alarmEventId = db.gv_alarm_event.insert(alarm);

  List<AlarmPlan> plans = db.gv_alarm_plan.matchByChannelAndFilters(
    alarm.channelId,
    alarm.level, alarm.method, alarm.type, alarm.eventtype
  );

  for (AlarmPlan plan : plans) {
    // 录像联动
    if (plan.record_duration_sec > 0) {
      startAlarmRecording(plan, alarm, alarmEventId);
    }

    // 快照联动
    if (plan.snapshot_interval_sec > 0) {
      startAlarmSnapshots(plan, alarm, alarmEventId);
    }
  }
}
```

### 4.2.2 录像联动：INVITE live → 流在线 → startRecord → stopRecord → BYE → 落库 record_file

```java
void startAlarmRecording(AlarmPlan plan, AlarmEvent alarm, long alarmEventId) {
  // 1) 建一个任务（用你 gv_record_task）
  long taskId = db.gv_record_task.insert({
    task_type: "alarm",
    device_id: alarm.deviceId,
    channel_id: alarm.channelId,
    start_time: now(),
    end_time: now().plusSeconds(plan.record_duration_sec),
    status: "pending"
  });

  // 2) 发起实时 INVITE 建立 live 流（这里是“实时直播请求”）
  InviteResult ir = gbInvite.live(alarm.deviceId, alarm.channelId); // -> dialogId/ssrc/streamId/app/vhost/mediaServerId
  db.gv_record_task.update(taskId, { status:"wait_stream", dialog_id: ir.dialogId, stream_id: ir.streamId, app: ir.app, vhost: ir.vhost });

  // 3) 轮询 ZLM 流在线（不依赖 hook）
  if (!zlm.waitOnline(ir.vhost, ir.app, ir.streamId, 10_000)) {
    gbInvite.bye(ir.dialogId);
    db.gv_record_task.fail(taskId, "stream not online");
    return;
  }

  // 4) startRecord（mp4）
  String customizedPath = "/record/alarm/" + alarmEventId + "/" + taskId + "/";
  zlm.startRecord(type=1, vhost=ir.vhost, app=ir.app, stream=ir.streamId, customized_path=customizedPath, max_second=0);
  db.gv_record_task.update(taskId, { status:"recording", customized_path: customizedPath });

  // 5) 到时停止（录像时长由预案决定）
  schedule(plan.record_duration_sec + 3 /*buffer*/, () -> {
    zlm.stopRecord(type=1, vhost=ir.vhost, app=ir.app, stream=ir.streamId);

    gbInvite.bye(ir.dialogId);  // 关闭实时直播（BYE）
    db.gv_record_task.update(taskId, { status:"finalizing" });

    // 6) 查 mp4 列表，选出本次文件
    Mp4File f = zlm.getMp4RecordFile(vhost=ir.vhost, app=ir.app, stream=ir.streamId,
                                     period=today(), customized_path=customizedPath)
                  .pickLatest();

    // 7) 落库 record_file + 关联 alarm_event
    long recordFileId = db.gv_record_file.insert({
      device_id: alarm.deviceId,
      channel_id: alarm.channelId,
      source_type: "alarm",
      start_time: epochSeconds(alarm.recvTime),
      end_time: epochSeconds(now()),
      duration: plan.record_duration_sec,
      video_path: f.path,
      file_size: f.size,
      vhost: ir.vhost, app: ir.app, stream_id: ir.streamId,
      source_id: alarmEventId, source_desc: "alarm_plan:" + plan.id
    });

    db.gv_alarm_event_asset.insert(alarmEventId, "record_file", recordFileId);
    db.gv_record_task.update(taskId, { status:"done" });
  });
}
```

### 4.2.3 快照联动：ZLM getSnap 按周期执行 + 落库 snapshot_file

```java
void startAlarmSnapshots(AlarmPlan plan, AlarmEvent alarm, long alarmEventId) {
  // 快照依赖“流存在”，两种策略：
  // A) 复用上面录像联动已经拉起来的 live 流
  // B) 如果没录像但要快照，也要单独拉 live 流（更简单：直接用 A 的 ir）

  LiveStreamRef lr = ensureLiveStreamForSnapshots(alarm); // 返回 vhost/app/streamId，可复用录像的流

  int totalSec = Math.max(plan.record_duration_sec, 10); // 你也可以单独配置快照持续时间
  for (int t = 0; t <= totalSec; t += plan.snapshot_interval_sec) {
    schedule(t, () -> {
      // ZLM getSnap：一般需要 url/vhost/app/stream/timeout 等参数，你用现有 client 封装
      SnapResult snap = zlm.getSnap(lr.vhost, lr.app, lr.streamId);

      long snapId = db.gv_snapshot_file.insert({
        device_id: alarm.deviceId,
        channel_id: alarm.channelId,
        source_type: "alarm",
        source_id: alarmEventId,
        shot_time: now(),
        file_path: snap.path,
        file_size: snap.size,
        format: snap.format,
        width: snap.width,
        height: snap.height,
        media_server_id: lr.mediaServerId,
        media_server_ip: lr.mediaServerIp,
        vhost: lr.vhost, app: lr.app, stream_id: lr.streamId
      });

      db.gv_alarm_event_asset.insert(alarmEventId, "snapshot", snapId);
    });
  }
}
```

## 最容易踩坑的 3 点（我帮你提前钉死口径）

1. **Catalog / Alarm / MobilePosition / PTZPosition** 这些订阅体里的 `CmdType` 必须对：标准里就是这么定义的。
2. 续订/退订**尽量复用 dialog**（Call-ID/Tag/CSeq），否则很多设备退订无效（一直推 NOTIFY）。
3. 报警联动录像/快照：你现在的目标是“资产落库”，所以务必用 `gv_record_task` 做状态机，不要在 NOTIFY 处理线程里阻塞等待。

---

必须使用 recordList 中返回的录像时间段（或其子集）来发起回放请求，否则设备会因“无录像数据”而立即结束流。





下面我按“**GB28181 网关**（SIP/媒体控制层）” vs “**业务 API**（策略/任务/资产/预案层）”把职责边界切干净，并把**哪些由网关执行、哪些由网关通过 hook 转发给业务、哪些必须业务 API 做**逐条对应到你前面 4 个场景。

---

## 1）总体原则：网关负责“协议与会话”，业务负责“策略与资产”

### 网关（GB28181 SIP Server / Media Gateway）做什么

* **SIP 注册/鉴权/保持在线**（REGISTER）
* **SUBSCRIBE / NOTIFY / MESSAGE 的协议处理**（订阅与事件接入）
* **INVITE / ACK / BYE / INFO**（点播、回放控制、实时流会话）
* **SSRC/streamId/port 分配、RTP 接收与转发到 ZLM**
* **对接 ZLM 的控制类接口**：startRecord/stopRecord/getMp4RecordFile/getSnap/close_stream…（可做，也可部分交给业务，但我建议网关做“媒体控制”）
* **维护 SIP dialog 状态**（Call-ID/FromTag/ToTag/CSeq），尤其是订阅续订/退订和回放 INFO 控制

### 业务 API 做什么

* 用户配置：**设备订阅开关**、**报警预案**、通道关联
* 落库：`gv_alarm_event / gv_record_task / gv_record_file / gv_snapshot_file / gv_alarm_event_asset`
* 决策：报警事件命中哪个预案、录像时长、快照周期、是否开启录制/抓拍
* 编排：创建任务、更新任务状态、失败重试、超时清理、生成下载链接
* 对外 REST：前端查询报警/录像/快照列表、下载回放、任务状态等

> 一句话：**网关是“执行器”，业务是“指挥官 + 账本”。**

---

## 2）网关通过 hook 转发给业务 API 的内容（业务只做“决策/入库”）

### 必须由网关 hook 给业务的事件（入站）

1. **设备上线/下线**

* REGISTER 成功 / keepalive 超时 / unregister
* 业务用途：展示在线状态、触发“补发订阅/补发预案联动”

2. **目录通知**

* NOTIFY（CmdType=Catalog）或 MESSAGE（部分厂商）
* 业务用途：更新通道表、设备目录缓存

3. **报警通知**

* NOTIFY / MESSAGE（CmdType=Alarm），携带 `AlarmPriority/AlarmMethod/AlarmType/EventType/Longitude/Latitude/AlarmDescription`
* 业务用途：落库 `gv_alarm_event`，匹配 `gv_alarm_plan`，创建录像/快照任务

4. **位置通知（MobilePosition）**

* NOTIFY（CmdType=MobilePosition）
* 业务用途：落库位置、轨迹、展示

5. **PTZ-2022 状态/位置信息（PTZPosition）**

* NOTIFY（CmdType=PTZPosition）
* 业务用途：展示云台状态、联动逻辑（可选）

> 这些都是“设备→平台”的上报，网关最适合第一时间解析并转发。

## 3）场景拆解：哪些网关做，哪些业务做

### 场景 1：用户对设备 340200... 订阅 4 项都设为 1

#### 业务 API 做

* 保存配置（例如 `device_subscribe_cfg` 表/字段）
* 生成“目标态”：catalog=on, alarm=on, mobile=on, ptz=on
* 调用网关的 **控制接口**（或写入命令队列）：

    * `POST /gw/devices/{deviceId}/subscriptions` body: {catalog:1, alarm:1, mobile:1, ptz:1, expires:3600}

#### 网关做

* 检查设备是否在线（REGISTER 表）
* 对每个事件类型发送 **SUBSCRIBE**：

    * Catalog / Alarm / MobilePosition / PTZPosition
* 保存每个订阅的 **dialog 信息**（call-id/tags/cseq/expires_at）
* SUBSCRIBE 200 OK 成功后回写订阅状态（可回调业务、或网关内部存 session）

> 订阅下发这件事本质是“协议会话”，**网关做**最稳。

---

### 场景 2：Schedule job：需要一个 job 一直拉取订阅或者关闭订阅？

**不需要“拉取订阅数据”**（数据是 NOTIFY 推送）。
需要的是“**续订/退订巡检**”。

#### 谁做 job？

两种都行，但我建议：

* **网关做**：因为续订/退订依赖 dialog（call-id/tags/cseq），网关掌握最完整
* 业务只保存“配置目标态”，网关自己根据 session 到期时间续订

#### 具体职责

* 网关 job（每分钟）：

    * `expires_at < now + 5min` → 复用 dialog 续订 SUBSCRIBE
    * 发现配置为 0 或设备离线长期 → 尝试 Expires=0 或标记 stopped
* 业务 job（可选）：

    * 只做“配置一致性审计”（比如提醒某设备订阅失败）

---

### 场景 3：用户把 4 项订阅都设为 0（取消订阅）

#### 业务 API 做

* 保存配置：catalog=0 alarm=0 mobile=0 ptz=0
* 调用网关：`POST /gw/devices/{deviceId}/subscriptions` body: 全 0

#### 网关做

* 对每个 ACTIVE session，复用 dialog 发送 **SUBSCRIBE Expires=0**（退订）
* 更新 session 状态为 STOPPED
* 如果设备离线：记录“待退订”，设备上线后补发 Expires=0（兜底）

### 场景 4：收到订阅数据转发给 API，格式是什么？以及直播/录像/快照怎么联动预案？

这里你要把“实时媒体控制”与“业务编排”分层。

#### 4.1 网关 → 业务 hook：转发格式（建议统一一套 envelope）

网关把原始 XML + 解析结构一起给业务，业务落库与匹配预案。

```json
{
  "event": "ALARM|CATALOG|MOBILE_POSITION|PTZ_POSITION",
  "deviceId": "34020000001320000109",
  "channelId": "xxx(如果能解析到)",
  "recvTime": "2026-01-22T10:11:12.123Z",
  "gb": {
    "cmdType": "Alarm",
    "sn": "62",
    "rawXml": "<Notify>...</Notify>"
  },
  "data": { "level":1, "method":5, "type":6, "eventtype":1, "longitude":..., "latitude":..., "description":"..." }
}
```

* 网关负责：解析、校验、200 OK 回复设备
* 业务负责：落库 `gv_alarm_event` + 预案匹配

#### 4.2 报警预案联动：谁来“启动直播/录像/快照”？

我建议统一：**业务决定，网关执行**。

**业务 API 做：**

1. 收到 hook(Alarm) → 插入 `gv_alarm_event`
2. 匹配 `gv_alarm_plan`（通道绑定 + level/method/type/eventtype JSON）
3. 如果需要录像：创建 `gv_record_task(task_type='alarm')`，状态 pending
4. 如果需要快照：创建快照任务（你可复用 `gv_record_task` 或单独表；简单点就直接调网关开始抓拍定时器）

**网关做：**

* 提供执行接口（被业务调用）：

    * `POST /gw/tasks/{taskId}/start-alarm-record`（或 `POST /gw/records/start`）
    * `POST /gw/tasks/{taskId}/stop`（或 stopRecord/bye/close_stream 打包）
    * `POST /gw/snap/get`（对接 ZLM getSnap）

**网关执行录像的动作链（业务只发命令+参数）：**

* 若“录像来自实时流”：

    1. INVITE live → 等流在线
    2. ZLM startRecord
    3. 到 `record_duration_sec + buffer`：stopRecord + BYE
    4. getMp4RecordFile 找到文件信息
    5. 回调业务：`record_done(taskId, fileMeta)`（或业务主动拉取）
* 若“录像来自设备回放下载”（你任务类型 playback_download）：

    1. 发 playback INVITE（带时间段）→ dialog_id
    2. 流在线 → startRecord
    3. 到 endTime：stopRecord + INFO teardown(dialog) / BYE
    4. getMp4RecordFile → 回调业务

**快照联动（ZLM getSnap）：**

* 业务决定快照周期/持续时长（通常=录像时长）
* 网关执行：

    * 若已有 live 流：直接对 vhost/app/stream 调 getSnap
    * 没有 live 流：先 INVITE live（短连接）→ 抓拍 → BYE

**业务落库：**

* 网关回调给业务 fileMeta/snapMeta 后：

    * 插入 `gv_record_file` 或 `gv_snapshot_file`
    * 插入 `gv_alarm_event_asset` 关联资源
    * 更新 `gv_record_task` 状态 done/failed

## 4）建议的接口边界（最清晰、最少扯皮）

### 业务 → 网关（控制类）

* `POST /gw/devices/{deviceId}/subscriptions` 设定目标态（1/0 + expires）
* `POST /gw/live/start`（deviceId, channelId）→ 返回 dialogId + streamInfo
* `POST /gw/live/stop`（dialogId）
* `POST /gw/record/start`（vhost/app/stream/customized_path/max_second）
* `POST /gw/record/stop`（vhost/app/stream）
* `POST /gw/snap/get`（vhost/app/stream）→ 返回图片路径/URL
* `POST /gw/task/execute`（taskId + 类型 + 参数）→ 网关执行并回调结果

### 网关 → 业务（hook 事件）

* `POST /api/gb/device-status`（online/offline）
* `POST /api/gb/notify`（Catalog/Alarm/MobilePosition/PTZPosition）
* `POST /api/gb/task-result`（record/snap 完成或失败）

## 5）一句话落地建议

* **订阅下发/续订/退订：网关全包**（业务只管“开关配置”）
* **NOTIFY 上报：网关解析并 hook 给业务**
* **报警联动录像/快照：业务决定、网关执行、业务落库**
