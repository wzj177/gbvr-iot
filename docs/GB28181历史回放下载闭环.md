## 一、先校准一个核心认知（非常重要）

> **GB28181 的回放 / 下载，本质是：
> 设备按你 INVITE 指定的时间段，把历史码流“实时吐出来”**

❗**没有“回放完成事件”**
❗**没有“文件完成回调”**
❗**没有“设备保证完整”的机制**

所以你只能靠 **时间 + RTP 状态 + 录制文件** 来推断完成。

你现在意识到这一点，是完全正确的。

---

## 二、ZLM 在这里到底是“什么角色”

你现在的架构里，ZLM 其实是：

```
GB 设备  --RTP-->  ZLM  --录制-->  文件
```

ZLM能给你的能力只有三类：

### 1️⃣ RTP 会话是否存在

* `getRtpInfo`
* `listRtpServer`

👉 判断：

* 设备是否已经开始推流
* 是否还在推

---

### 2️⃣ 录制控制（这是你要用的）

* `startRecord`
* `stopRecord`
* 录制类型：`mp4 / hls / ts`

⚠️ ZLM **不会**告诉你：

* “这是不是回放”
* “回放时间段是啥”
* “什么时候回放结束”

---

### 3️⃣ 文件结果

* 你只能**从文件系统 / 文件时长反推**

---

## 三、你现在方案的评价（说实话）

> **结论：能跑，但有 2 个致命风险**

### 👍 优点

* 不依赖 hook（非常好）
* 状态可控
* 任务模型清晰
* 适合私有部署 / 政企环境

### ⚠️ 风险点

#### ❌ 风险 1：

**“调用 startRecord 的时机可能不准”**

你现在是：

```
handleInviteResponse
  -> 写任务
  -> schedule job
      -> getRtpInfo
          -> 有就 startRecord
```

问题是：

> 有些设备 **RTP 已经来了，但关键 I 帧还没来**

这会导致：

* MP4 文件能生成
* 但前几秒是黑屏 / 无法播放

---

#### ❌ 风险 2：

**“用录制时长 ≈ 回放时间判断结束”不稳**

现实情况：

* 网络抖动
* 设备中途停顿
* 有些设备会提前结束
* 有些设备会多吐几秒

## 五、推荐的完整回放下载流程（不使用 hook）

### ① 用户发起回放 / 下载

API 创建一条任务：

```text
record_task
- task_id
- device_id
- channel_id
- start_time
- end_time
- ssrc
- stream_id
- status = INIT
```

---

### ② SIP INVITE（回放）

SDP 关键点：

```sdp
a=recvonly
t=开始时间 结束时间
y=ssrc
```

状态：

```
status = INVITE_SENT
```

---

### ③ 收到 200 OK（handleInviteResponse）

⚠️ **此时不要马上 startRecord**

只做：

```
status = SDP_OK
```

---

### ④ 定时任务：等待“稳定 RTP”

**轮询 ZLM：**

```http
GET /index/api/getRtpInfo?stream_id=xxx
```

判断条件（建议）：

* RTP 存在
* 已接收数据 > N KB（比如 1~2MB）
* 已持续 ≥ 2 秒

✔️ 满足后：

```http
startRecord(mp4)
```

并记录：

```
record_start_time = now()
status = RECORDING
```

👉 这一点**非常关键**，能避免黑屏文件

---

### ⑤ 监控回放结束（核心逻辑）

不用 hook，你只能靠 **RTP 活跃度**：

#### 定时轮询（1~2s）

```http
getRtpInfo
```

判断 **“结束”条件**：

满足任意一个即可：

#### ✅ 条件 A（最可靠）

* RTP Server 不存在了（设备 BYE / ZLM 释放）

#### ✅ 条件 B（兜底）

* RTP 存在
* 但 `lastRecvTime > 5~10 秒`
* 且已录制 ≥ 80% 期望时长

---

### ⑥ 停止录制 + 校验文件

```http
stopRecord
```

然后：

* 获取 MP4 文件
* 用 ffprobe / 文件时长
* 校验：

```text
abs(file_duration - (end - start)) < 容忍阈值
```

成功：

```
status = SUCCESS
```

失败：

```
status = FAILED / PARTIAL
```

---

## 六、你现在方案需要改的 3 个点（重点）

### ✅ 改 1：startRecord 一定要延迟

不要“RTP 一出现就录”，要等稳定。

---

### ✅ 改 2：不要只用「录制时长」判断结束

要结合：

* RTP 消失
* RTP 不再增长
* 期望时间

---

### ✅ 改 3：SSRC / stream_id 要作为**唯一主键**

不要靠 device_id + channel_id 推断

---

## 七、关于“回放下载 vs 实时回放”

建议你直接拆成两种任务类型：

```text
task_type:
- playback_preview   （不录）
- playback_download  （录制）
```

逻辑会干净很多。
