# GB28181 语音对讲 - 网关测试建议

本文档提供 GB28181Gateway (SIP 网关) 相关的测试建议和验证步骤，用于验证语音对讲功能与 API 层的集成。

> **注意**: 本文档仅提供测试建议，不涉及 Gb28181Gateway 模块的代码修改。网关架构已确认正确，以下是基于新 API 层实现的测试验证点。

---

## 一、网关职责概述

Gb28181Gateway (独立的 SIP 服务器进程) 负责以下功能：

1. **SIP 信令处理**：INVITE、BYE、200 OK、486 Busy 等消息
2. **设备通信**：与 GB28181 设备建立 SIP 会话
3. **状态同步**：通过 HTTP Hook 向 API 层上报 SIP 事件
4. **媒体协商**：SDP 协商，确定 RTP 参数

**API 层与网关的交互方式**：
- API 层通过 Redis 队列发送 SIP 命令到网关
- 网关通过 HTTP Hook 回调 API 层报告 SIP 事件
- 媒体流通过 ZLMediaKit 处理，不经过网关

## 二、网关测试场景

### 2.1 流到达处理测试 (on_publish Hook)

**测试目的**：验证网关正确处理 ZLM 的 on_publish 事件并触发 API 层的 `handleStreamArrival`

**测试步骤**：

1. **前置条件**：
   - GB28181 设备在线
   - ZLMediaKit 运行正常
   - 调用 `POST /api/v2/gb28181/devices/{deviceId}/channels/{channelId}/voice/prepare`

2. **执行操作**：
   - 前端使用返回的推流地址开始推流 (WebRTC/RTMP)
   - 等待 ZLM 触发 `on_publish` hook

3. **验证点**：

| 验证项 | 预期结果 | 检查方式 |
|--------|----------|----------|
| 会话状态转换 | `waiting_stream` → `stream_arrived` | 查询 `gv_voice_sessions` 表 |
| SIP INVITE 发送 | 网关向设备发送 INVITE | 查看网关日志 |
| RTP 端口分配 | `startSendRtpPassive` 成功调用 | 查看 API 日志 |

**网关日志关键词**：
- `收到流发布事件`
- `app=talk, stream=...`
- `准备语音对讲流到达处理`

### 2.2 SIP 200 OK 回调测试

**测试目的**：验证网关正确处理设备的 200 OK 响应并触发 API 层的 `onSipResponseOk`

**测试步骤**：

1. **前置条件**：
   - 会话状态为 `inviting`
   - SIP INVITE 已发送到设备

2. **执行操作**：
   - 设备响应 200 OK（需要实际设备或模拟器）
   - 网关收到 200 OK

3. **验证点**：

| 验证项 | 预期结果 | 检查方式 |
|--------|----------|----------|
| 会话状态转换 | `inviting` → `connected` | 查询 `gv_voice_sessions` 表 |
| dialog_id 保存 | `dialog_id` 字段已更新 | 查询 `gv_voice_sessions` 表 |
| call_id 保存 | `call_id` 字段已更新 | 查询 `gv_voice_sessions` 表 |
| sendRtpInfo 保存 | Redis 中存在 sendRtpInfo | 查询 Redis `GBVRIOT_SEND_RTP_INFO_CALL_ID` |

**网关日志关键词**：
- `收到 200 OK 响应`
- `dialog_id=...`
- `调用 API 回调通知成功`

### 2.3 流离开处理测试 (on_unpublish Hook)

**测试目的**：验证网关正确处理 ZLM 的 on_unpublish 事件并触发 API 层的 `handleStreamDeparture`

**测试步骤**：

1. **前置条件**：
   - 语音对讲已建立（状态为 `connected`）
   - 前端正在推流

2. **执行操作**：
   - 前端停止推流
   - 等待 ZLM 触发 `on_unpublish` hook

3. **验证点**：

| 验证项 | 预期结果 | 检查方式 |
|--------|----------|----------|
| 会话状态转换 | `connected` → `ended` | 查询 `gv_voice_sessions` 表 |
| ended_reason | `stream_departure` | 查询 `gv_voice_sessions` 表 |
| SIP BYE 发送 | 网关向设备发送 BYE | 查看网关日志 |
| SSRC 释放 | SSRC 已归还池中 | 查询 Redis `GBVRIOT_SSRC_INFO_*` |

**网关日志关键词**：
- `收到流停止发布事件`
- `app=talk, stream=...`
- `清理语音对讲会话`

### 2.4 BYE 消息发送测试

**测试目的**：验证网关正确发送 SIP BYE 消息

**测试步骤**：

1. **前置条件**：
   - 会话状态为 `connected`
   - `dialog_id` 已保存

2. **执行操作**：
   - 调用 `POST /api/v2/gb28181/voice/{sessionId}/stop`

3. **验证点**：

| 验证项 | 预期结果 | 检查方式 |
|--------|----------|----------|
| SIP BYE 发送 | 网关发送 BYE 到设备 | 查看网关日志 |
| 设备响应 | 收到设备 200 OK | 查看网关日志 |
| 会话状态 | `ended` | 查询 `gv_voice_sessions` 表 |

**网关日志关键词**：
- `发送 BYE 消息`
- `dialog_id=...`
- `设备响应 200 OK`

### 2.5 超时处理测试

**测试目的**：验证网关正确处理超时场景

**测试步骤**：

1. **场景 A：推流超时**
   - 调用 `prepareTalk` 获取推流地址
   - 不推流，等待 15 秒超时
   - 验证会话状态变为 `failed`，`ended_reason=timeout`

2. **场景 B：SIP 响应超时**
   - 推流后，等待 INVITE 发送
   - 设备不响应（或断网）
   - 验证会话状态变为 `failed`，`ended_reason=timeout`

**验证点**：

| 验证项 | 预期结果 | 检查方式 |
|--------|----------|----------|
| 会话状态 | `failed` | 查询 `gv_voice_sessions` 表 |
| ended_reason | `timeout` | 查询 `gv_voice_sessions` 表 |
| 资源清理 | SSRC 已释放，BYE 未发送 | 查看 Redis、网关日志 |

## 三、预期网关行为

基于新的 API 层实现，网关应该表现出以下行为：

### 3.1 正常流程

```
API: prepareTalk() -> 返回推流地址
前端: 开始推流
ZLM: on_publish -> 网关 -> API: handleStreamArrival()
网关: 发送 INVITE -> 设备
设备: 200 OK -> 网关 -> API: onSipResponseOk()
状态: connected
```

### 3.2 停止流程

```
API: stopVoiceTalk() -> stopVoiceTalkBySession()
网关: 发送 BYE -> 设备
ZLM: on_unpublish -> 网关 -> API: handleStreamDeparture()
状态: ended
资源清理: SSRC 释放、RTP 停止、sendRtpInfo 删除
```

### 3.3 异常流程

```
超时场景:
定时任务: processTimeouts() -> 标记会话为 failed
API: stopVoiceTalkBySession() 清理资源
网关: 不发送 BYE（因为可能无 dialog）
```

## 六、故障排查

### 6.1 会话卡在 waiting_stream

**可能原因**：
1. 前端未推流
2. ZLM hook 未触发
3. 网关未收到 on_publish 事件

**排查步骤**：
1. 检查 ZLM 是否收到推流：`curl http://zlm:80/index/api/getMediaList?app=talk&stream=xxx`
2. 检查网关日志是否有 on_publish 事件
3. 检查 API 日志是否有 `语音流到达` 记录

### 6.2 会话卡在 inviting

**可能原因**：
1. 设备未响应 INVITE
2. 网关未发送 INVITE
3. 设备离线

**排查步骤**：
1. 检查网关日志是否已发送 INVITE
2. 检查设备状态：`GET /api/v2/gb28181/devices/{deviceId}`
3. 检查网络连通性

### 6.3 资源未释放

**可能原因**：
1. CAS 更新失败
2. 异常导致清理逻辑未执行

**排查步骤**：
1. 检查 `gv_voice_sessions` 表是否有僵尸会话（非 ended 状态但已过期）
2. 检查 Redis 中是否有残留的 sendRtpInfo
3. 手动调用 stopVoiceTalk 清理

## 八、与 API 层的集成验证

### 8.1 验证状态机转换

在 `gv_voice_sessions` 表中验证状态流转：

```
waiting_stream (created_at)
  ↓ on_publish
stream_arrived (updated_at)
  ↓ startSendRtpPassive
inviting (expires_at 更新)
  ↓ 200 OK
connected
  ↓ stop / stream_departure
ended (ended_at, ended_reason)
```

### 8.2 验证 CAS 操作

检查 `version` 字段是否递增：

```sql
SELECT id, session_id, status, version, created_at, updated_at
FROM gv_voice_sessions
ORDER BY id DESC
LIMIT 10;
```

每次状态更新，`version` 应该 +1。

### 8.3 验证资源清理

检查以下资源是否正确释放：

1. **SSRC**：Redis `GBVRIOT_SSRC_INFO_*`
2. **sendRtpInfo**：Redis `GBVRIOT_SEND_RTP_INFO_CALL_ID`
3. **RTP 端口**：ZLM `closeRtpServer` 调用
4. **SIP Dialog**：网关发送 BYE
