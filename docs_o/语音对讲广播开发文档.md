# GB28181 语音对讲/广播 开发文档

> 最后更新：2026-02-26

## 一、协议概述

GB28181-2016 定义了两种语音模式：

| 模式 | 方向 | SDP direction | 说明 |
|------|------|--------------|------|
| **broadcast（广播）** | 服务端 → 设备（单向） | recvonly（设备视角） | 服务端推音频给设备播放 |
| **talk（对讲）** | 双向 | sendrecv | broadcast + 点播音频，实现双向对讲 |

### Talk 模式的完整流程（协议定义）

1. 用户端向设备通过视音频点播请求音频数据（**上行：设备 → 服务端**）
2. 用户端接收音频数据并通过播放设备播放
3. 用户端向设备发送广播请求（**下行：服务端 → 设备**）
4. 设备解析广播成功后通过 INVITE 方法向用户请求音频数据
5. 用户通过音频采集设备获取音频数据
6. 用户将采集的音频数据发送至设备

**本质**：talk = broadcast（下行推音频） + play（上行收音频），是两路独立的 RTP 流。

### WVP 实现方案（本项目对齐）

WVP 只处理了与 broadcast 相同的下行推音频逻辑，因为：
- 视频点播本身已包含设备音频（上行已有）
- talk 模式在 GB28181-2022 中已移除
- 两种模式使用相同逻辑，简化实现

**结论**：talk 和 broadcast 都走 Broadcast 流程（设备发起 INVITE）。

## 四、ZLM API 参数说明

### startSendRtpPassive（被动推流）

在设备 INVITE 到达后调用，ZLM 监听本地端口等待设备连接。

```
参数映射（SendRtpDo）:
  app             = session.mode ("talk" 或 "broadcast")  ← ZLM 应用名
  stream          = session.stream                        ← 用户推流的源流（ZLM 从此流读取音频发给设备）
  ssrc            = session.ssrc                          ← SSRC（10位：1位类型 + 5位域 + 4位序列）
  recv_stream_id  = session.receive_stream                ← 设备推回的音频流名（带 _recv 后缀，避免冲突）
  src_port        = session.rtp_port                      ← ZLM 监听端口
  pt              = 8                                     ← PCMA (a=rtpmap:8 PCMA/8000)
  use_ps          = false                                 ← 语音不用 PS 封装
  only_audio      = true                                  ← 仅音频
  is_tcp          = 由设备 SDP 决定                        ← TCP or UDP
```

### Stream ID 命名规则

```
用户推流:   {mode}_{deviceId}_{channelId}          例: talk_34020000001320000001_34020000001320000001
设备收流:   {mode}_{deviceId}_{channelId}_recv      例: talk_34020000001320000001_34020000001320000001_recv
```

`_recv` 后缀确保 `stream` 和 `recv_stream_id` 不冲突。

## 五、SSRC 分配规则

格式：`T + DDDDD + NNNN`（共10位十进制数字）

| 前缀(T) | 用途 | 工厂方法 |
|---------|------|---------|
| 0 | 视频预览 | `getPlaySsrc()` |
| 1 | 录像回放 | `getPlayBackSsrc()` |
| 2 | 语音对讲 | `getTalkSsrc()` |
| 3 | 语音广播 | `getBroadcastSsrc()` |
| 4 | 录像下载 | `getDownloadSsrc()` |

- `DDDDD`：SIP 域编码第 4-8 位（`substr($sipDomain, 3, 5)`）
- `NNNN`：序列号 0001-9999（`MAX_STREAM_COUNT = 10000`）
- SSRC 池使用 Redis Set 存储，sPop 分配，sAdd 回收

## 六、SDP 方向属性

### Broadcast MESSAGE 阶段

不包含 SDP，只有 XML 通知：
```xml
<Notify>
  <CmdType>Broadcast</CmdType>
  <SN>123456</SN>
  <SourceID>{服务端SIP ID}</SourceID>
  <TargetID>{通道ID}</TargetID>
</Notify>
```

### 200 OK SDP（服务端回复设备 INVITE）

始终使用 `a=sendonly`（服务端只发送，设备只接收），与 WVP 一致：
```
v=0
o={serverId} 0 0 IN IP4 {mediaIp}
s=Broadcast
c=IN IP4 {mediaIp}
t=0 0
m=audio {localPort} TCP/RTP/AVP 8
a=rtpmap:8 PCMA/8000/1
a=sendonly
a=setup:passive
y={ssrc}
f=v/////a/1/8/1
```

### mapModeToSdpDirection 映射

用于 Broadcast MESSAGE 阶段的 `sdp_direction` 字段（存入 pendingBroadcasts）：

| mode | sdp_direction | 含义 |
|------|--------------|------|
| broadcast | recvonly | 设备只接收 |
| talk | sendrecv | 设备双向收发 |

> 注意：200 OK SDP 硬编码为 `sendonly`，不使用此字段。

## 七、会话状态机

```
CREATED → STREAM_ARRIVED → INVITING → CONNECTED → CLOSED
                                ↓
                             FAILED
```

| 状态 | 触发 | 说明 |
|------|------|------|
| CREATED | `startVoiceTalk()` | 创建会话，分配 RTP 端口 |
| STREAM_ARRIVED | `handleStreamArrival()` | 前端推流到达 ZLM |
| INVITING | Handler 处理完成 | 已发 Broadcast MESSAGE，等待设备 INVITE |
| CONNECTED | `onSipResponseOk()` | 设备 200 OK / ACK 完成，音频推流中 |
| CLOSED | `stopVoiceTalkBySession()` | BYE 发送，资源释放 |
| FAILED | 各种异常 | 超时、流中断、ZLM 失败等 |

## 八、Bug 修复记录

### Bug 1：Broadcast 410 Gone（pendingBroadcast app 字段错误）

**现象**：设备 INVITE 到达后，网关回调 `broadcast_setup_rtp`，API 返回 `stream_ready=false`，网关回 410 Gone。

**原因**：`CommandDispatcher.handleVoiceBroadcast()` 中 `pendingBroadcast['mode']` 存的是 SDP direction（如 `recvonly`），而非 ZLM app 名（`broadcast`/`talk`）。在 `isStreamReady()` 检查时用 `recvonly` 作为 app 名去查 ZLM，找不到流。

**修复**：
- `CommandDispatcher.php`：新增 `'app'` 字段存 ZLM 应用名，`'mode'` 保留 SDP direction
- `GB28181Handler.php`：`broadcast_setup_rtp` 任务使用 `pendingBroadcast['app']`

### Bug 2：SSRC 溢出（超过 32 位整数）

**现象**：分配的 SSRC 超过 10 位数字，导致 SDP 解析异常。

**原因**：`SSRCFactory::MAX_STREAM_COUNT = 100000`，`sprintf('%04d', 10000+)` 产生 5+ 位序列号，总 SSRC 达 11 位，超过 `2^31 - 1`。

**修复**：`SSRCFactory.php`：`MAX_STREAM_COUNT` 从 `100000` 改为 `10000`。

### Bug 3：Talk 模式流程错误 + ZLM 参数反转

**现象**：Talk 模式使用服务端发起 INVITE（`TalkStreamArrivalHandler`），且 `startSendRtpPassive` 的 `stream` 和 `recv_stream_id` 参数互换。

**原因**：
1. Talk 模式错误使用了服务端发 INVITE 流程，应与 broadcast 一样由设备发 INVITE
2. `Gb28181Service.handleVoiceTalkStreamArrival()` 中 `createPassive()` 的 `stream` 传了 `receiveStreamId`，`setRecvStreamId()` 传了 `stream`——反了
3. `setupBroadcastRtp()` 回退生成的 `receiveStreamId` 缺少 `_recv` 后缀，与 `stream` 同名导致冲突

**修复（4 处）**：

1. **`VoiceTalkServiceImpl.php` - `handleStreamArrival()`**：`receiveStreamId` 加 `_recv` 后缀
```php
$receiveStreamId = $this->generateStreamId(...) . '_recv';
```

2. **`VoiceTalkServiceImpl.php` - `resolveStreamArrivalHandler()`**：talk/broadcast 统一路由到 `BroadcastStreamArrivalHandler`
```php
// 之前: talk → TalkStreamArrivalHandler（服务端发 INVITE）
// 现在: 统一 → BroadcastStreamArrivalHandler（设备发 INVITE）
return new BroadcastStreamArrivalHandler($this->bfw);
```

3. **`Gb28181Service.php` - `handleVoiceTalkStreamArrival()`**：修正参数顺序
```php
// 之前（错误）: stream=receiveStreamId, recv_stream_id=stream
// 现在（正确）: stream=stream（用户推流源）, recv_stream_id=receiveStreamId（设备收流名）
$sendRtpDo = SendRtpDo::createPassive($dto->getApp(), $dto->getStream(), $dto->getSsrc())
    ->setRecvStreamId($dto->getReceiveStreamId());
```

4. **`VoiceTalkServiceImpl.php` - `setupBroadcastRtp()`**：回退值加 `_recv` 后缀
```php
$receiveStreamId = $session['receive_stream']
    ?: $this->generateStreamId(...) . '_recv';
```

## 九、测试检查清单

### 部署前
- [ ] 重启 API 服务：`php start.php restart`

- [ ] 确认 ZLMediaKit 运行中
- [ ] 重置 SSRC 池（如果之前有溢出数据）

### Broadcast 测试
- [ ] 前端发起广播请求
- [ ] 确认 ZLM on_publish Hook 触发
- [ ] 确认 SIP MESSAGE (CmdType=Broadcast) 发送成功
- [ ] 确认设备发送 INVITE
- [ ] 确认 broadcast_setup_rtp 回调：`startSendRtpPassive` 成功，返回 `local_port`
- [ ] 确认 200 OK SDP 正确：`a=sendonly`，端口/SSRC 正确
- [ ] 确认设备 ACK
- [ ] 确认 `startSendRtp` 触发（ACK 后或立即）
- [ ] 确认设备端音频播放正常
- [ ] 停止广播，确认 BYE 发送、SSRC 回收、会话关闭

### Talk 测试
- [ ] 前端发起对讲请求（mode=talk）
- [ ] 确认流程与 Broadcast 一致（走 BroadcastStreamArrivalHandler）
- [ ] 确认 ZLM app 名为 `talk`（非 `broadcast`）
- [ ] 确认设备端音频播放正常
- [ ] 如需双向音频：确认视频点播已拉取设备音频流

### 异常场景
- [ ] 前端推流后立即断开 → 设备 INVITE 时 `stream_ready=false` → 410 Gone
- [ ] 设备超时未发 INVITE → 超时定时器触发清理
- [ ] 同设备同通道重复发起 → 冲突检查拒绝或清理僵尸会话
- [ ] TCP 模式对讲 → 确认 `is_tcp=true`，SDP 含 `a=setup:passive/active`
